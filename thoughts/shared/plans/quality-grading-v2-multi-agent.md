# Quality Grading v2: Multi-Agent Assessment Pipeline

## Problem Statement

The current quality grading system stuffs ~72K tokens of pre-collected static evidence into a single prompt, then asks one agent to score everything. This is:

1. **Wasteful** — 55% of the token budget is a `tree` blob with function signatures the agent doesn't use for scoring
2. **Shallow** — the agent analyzes pre-collected data instead of actually running tools (`cargo test`, `go test`, coverage generators)
3. **Monolithic** — one agent scores 9 dimensions across domains and repo-wide, making it hard to improve any single dimension's assessment
4. **Static** — test coverage is estimated by file-pairing heuristics instead of measured by running the actual test suite

## Vision

Split each scoring dimension into its own specialist agent. Each agent:
- Gets a focused prompt for its dimension only
- Has tool access to read files, run shell commands, and use repo-native tooling
- Produces a standalone assessment document
- Runs in parallel with the other dimension agents

A final **synthesizer agent** receives all dimension reports and compiles the quality grade document.

## What Each Agent Gets

### Shared Context (lightweight, ~2-5K tokens)

Every dimension agent receives the same minimal repo context:

1. **Tree diagram** — an `ls -R`-style directory listing, NOT the current JSON blob with signatures. Something like:
   ```
   .
   ├── scripts/
   │   └── fixtures/
   ├── tools/
   │   └── gardener/
   │       ├── src/
   │       │   ├── agent/
   │       │   ├── quality_*.rs
   │       │   └── ...
   │       └── Cargo.toml
   └── docs/
   ```
   Target: under 3K chars for this repo. Generated by walking the filesystem, not serializing a struct.

2. **Language summary** — just the language breakdown (`Rust: 95 files, Shell: 12 files, TOML: 5 files`)

3. **Package manifests** — names and paths only (no content)

### Per-Dimension Context

Each agent gets additional context specific to its job. But the key shift is: **agents discover information using tools, not by reading pre-collected JSON**.

## Dimension Agents

### 1. `test_coverage` Agent

**Prompt focus**: Measure actual test coverage for each language in the repo.

**What it should do**:
- Identify languages and their test frameworks
- Run coverage tools natively: `cargo tarpaulin`, `go test -cover`, `pytest --cov`, `jest --coverage`, etc.
- If native coverage tools aren't available/configured, fall back to gardener's untested-file detection tool
- Report coverage percentages per domain
- Score: based on actual measured coverage, not file-pairing heuristics

**Pre-provided**: list of detected languages, test runner commands if found in CI config

### 2. `test_quality` — Hybrid (Deterministic + Sampled Agent Check)

**Prompt focus**: Assess how thorough and well-structured tests are.

**Strategy**: Two-phase approach to stay fast while still catching nuance.

**Phase 1 — Deterministic (all test files)**:
- Assertion density per test file (already exists in `quality_assertion_counter.rs`)
- Test type classification: unit vs integration vs e2e (already exists in `quality_test_detector.rs`)
- Test helper/fixture/mock detection via path and import patterns
- Ratio of test files to source files per domain
- Output: a deterministic base score + a ranked list of test files sorted by "interest" (high assertion count, integration tests, edge-case-looking names)

**Phase 2 — Agent spot-check (sampled subset)**:
- Take the top N test files from the ranked list (N sized to fit comfortably in context — probably 5-10 files, ~500 lines total)
- Agent reads them and assesses: are these tests actually testing meaningful behavior? Are assertions substantive or trivial? Are edge cases covered?
- Agent can adjust the deterministic score up or down by a bounded amount (e.g., ±15 points)
- This keeps the agent's job small and focused: "here are the stats, here are the files — validate or challenge the score"

**Pre-provided**: deterministic metrics summary, sampled test file contents (pre-read by orchestrator to avoid agent file I/O overhead)

### 3. `risk_exposure` — Hybrid (Deterministic Complexity + Agent Review)

**Prompt focus**: Identify areas of the codebase most exposed to bugs and regressions.

**Phase 1 — Deterministic complexity analysis (new tool)**:
- Add a `quality_complexity_analyzer.rs` that computes per-file complexity metrics:
  - Line count (already have this)
  - Nesting depth (count max indent level or brace depth)
  - Cyclomatic complexity proxy: count branch keywords (`if`, `match`, `else`, `for`, `while`, `?`, `unwrap`) per file
  - Function count and avg function length
- Cross-reference with untested file list (already have this from `quality_untested_finder.rs`)
- Cross-reference with debt markers (already have this from `quality_debt_scanner.rs`)
- Output: ranked list of "riskiest" files — complex + untested + debt-laden

**Phase 2 — Agent spot-check**:
- Agent receives the risk-ranked file list with metrics
- Reads a sample of the top-risk files (fits in context)
- Evaluates: error handling gaps, missing validation at boundaries, unsafe patterns
- Confirms or adjusts the deterministic risk score

**Pre-provided**: complexity metrics, debt marker summary, untested file list, sampled high-risk file contents

**Score**: based on density of risk indicators in untested/complex code, validated by agent

### 4. `convention_adherence` Agent

**Prompt focus**: Does the codebase follow its own stated conventions?

**What it should do**:
- Read steering docs (AGENTS.md, CLAUDE.md, CONTRIBUTING.md) for stated conventions
- Spot-check source files for compliance
- Run linters if configured and check for violations
- Score: based on gap between stated conventions and actual practice

**Pre-provided**: steering doc paths, linter config paths

### 5. `agent_steering` Agent

**Prompt focus**: How effectively do the steering docs guide autonomous agents?

**Rubric informed by research** (see Research section below):

- **Specificity over comprehensiveness**: Does the file contain concrete, actionable directives ("run tests with `make test`", "use `uv` not `pip`") vs vague overviews?
- **Signal-to-noise ratio**: Is the file concise (<300 lines ideally, <500 max) or bloated with LLM-generated boilerplate?
- **Architecture pointers**: Does it describe module boundaries and where to find things? (72.6% of effective files include this)
- **Testing/build commands**: Are the exact commands specified? (75% of effective files)
- **Progressive disclosure**: Does it link to deeper docs rather than inlining everything?
- **Absence of anti-patterns**: No auto-generated overviews, no duplicated README content, no walls of text
- **Cross-tool compatibility**: Is the guidance tool-agnostic or locked to one agent?

Score anchors:
- **90-100**: Concise, specific, actionable. Contains architecture map, build/test commands, conventions. Links to deeper docs. Under 300 lines.
- **70-89**: Good content but some bloat, or missing one key category (architecture, testing, conventions).
- **50-69**: Present but generic. Overviews without actionable directives. Or over-long with buried signals.
- **30-49**: Minimal — exists but provides little value beyond "this is a Python project."
- **0-29**: Missing or effectively empty.

**What it should do**:
- Read all steering docs
- Evaluate against the rubric above
- Check readability (Flesch score proxy: sentence length, jargon density)
- Assess whether the docs actually reduce agent exploration overhead

**Pre-provided**: paths to all steering doc files

### 6. `mechanical_guardrails` Agent

**Prompt focus**: Are there automated checks preventing bad code from landing?

**What it should do**:
- Check for linter configs (.eslintrc, clippy.toml, .golangci.yml, etc.)
- Check for pre-commit hooks (.pre-commit-config.yaml, .husky/, git hooks)
- Check for CI pipeline configs (.github/workflows/, .gitlab-ci.yml)
- Check for type checking configs (tsconfig strict mode, mypy.ini)
- Try running linters to see if they pass
- Score: based on breadth and enforcement level of automated checks

**Pre-provided**: CI/lint detection summary

### 7. `local_feedback_loop` Agent

**Prompt focus**: Can a developer/agent get fast local feedback?

**What it should do**:
- Try running the test suite and measure execution time
- Check for watch-mode configs
- Look for Makefile/justfile/package.json scripts
- Check if CI commands can be run locally
- Score: based on how quickly and easily you can validate changes locally

**Pre-provided**: detected CI config, Makefile/justfile paths

### 8. `coverage_infrastructure` Agent

**Prompt focus**: Is coverage tracked and enforced?

**What it should do**:
- Look for coverage tool configs (tarpaulin.toml, .coveragerc, jest.config coverage settings)
- Check CI for coverage reporting steps
- Look for coverage thresholds/gates
- Check for coverage badges or reporting integrations
- Score: based on whether coverage is measured, reported, and enforced

**Pre-provided**: coverage detection summary

### 9. `documentation_quality` Agent

**Prompt focus**: How well-documented is the codebase?

**What it should do**:
- Assess README quality and completeness
- Check for API docs, architectural docs
- Look at inline documentation density in key files
- Check for doc generation configs (rustdoc, godoc, typedoc)
- Score: based on documentation breadth, quality, and accessibility

**Pre-provided**: doc file inventory

## Orchestrator Changes

### Step 0: Deterministic pre-computation (~5s)

Before any agents run, the Rust orchestrator:

1. Generates the shared context (tree diagram + language summary) — no LLM
2. Runs deterministic analyzers that feed into hybrid dimensions:
   - `quality_complexity_analyzer.rs` (new) — per-file complexity metrics
   - `quality_assertion_counter.rs` — assertion density stats
   - `quality_test_detector.rs` — test classification
   - `quality_untested_finder.rs` — untested file list
   - `quality_debt_scanner.rs` — debt markers
3. Pre-reads sampled file contents for hybrid agents (test_quality, risk_exposure) so agents don't waste turns on file I/O

### Step 1: Domain discovery agent (~10-15s)

A lightweight agent receives the tree diagram + language summary and produces:
- Named domains with directory boundaries
- Brief domain descriptions
- This runs sequentially — dimension agents need its output

### Step 2: Spawn dimension agents in parallel (~60s budget)

The Rust orchestrator:

1. Spawns all 9 dimension agents in parallel using `std::thread::scope` (pattern already exists in `worker_pool.rs`)
2. Each agent receives: shared context + domain list + its dimension-specific pre-computed data
3. Hybrid agents (test_quality, risk_exposure) get pre-read file samples in their prompt
4. Each agent writes its report to `.cache/gardener/quality/<dimension>.md`
5. Waits for all agents to complete with a hard 60s wall-clock timeout
6. If any agent fails or times out, the entire assessment fails with a clear error message — no silent fallback

### Step 3: Synthesizer agent (~15s budget)

Once all dimension reports are collected:

1. Concatenate all dimension reports into the synthesizer prompt
2. The synthesizer extracts scores, compiles the summary, and produces the final JSON payload
3. The JSON is parsed exactly as today (between `<<GARDENER_JSON_START>>` / `<<GARDENER_JSON_END>>` markers)

### Step 4: Render output

Same as today, but the final document:
- Has a summary section with the grade table
- Links to each dimension report for details
- Dimension reports are human-readable standalone documents

### Total time budget: 90s

| Step | Budget | Notes |
|------|--------|-------|
| Deterministic pre-computation | ~5s | No LLM, pure Rust |
| Domain discovery agent | ~10-15s | Sequential, lightweight |
| Dimension agents (parallel) | ~60s | All 9 run concurrently |
| Synthesizer agent | ~15s | Single agent, reports-only input |
| **Total** | **~90s** | Hard cap enforced by orchestrator |

## Research: Agent Steering Docs

Key findings from recent ArXiv papers (2025-2026) that should inform the `agent_steering` rubric:

### What actually works (arXiv:2601.20404)
- AGENTS.md reduces output tokens 16-20% and completion time ~28%
- Mechanism: fewer planning iterations, less exploratory navigation
- Most impactful categories: coding conventions, architecture, project structure

### What doesn't work (arXiv:2602.11988)
- LLM-generated context files *reduced* success rates by ~3% while increasing costs 20%+
- Developer-written files: only ~4% improvement
- Codebase overviews don't help agents find files faster
- **Less prescriptive guidance outperforms comprehensive context files**

### Structural patterns (arXiv:2511.12884, arXiv:2511.09268)
- Architecture appears in 72.6% of effective files
- Testing commands in 75%
- Security/performance guidance severely underrepresented (14.5% each)
- Claude Code files tend toward "very difficult to read" readability scores
- Files accumulate content without systematic revision — maintenance debt

### Practitioner consensus
- Keep under 150 lines
- Use progressive disclosure — link to deeper docs, don't inline everything
- Specific tooling directives ("use `uv` not `pip`") are universally agreed to be valuable
- General overviews are where the evidence is mixed
- Don't auto-generate with `/init` — write every line deliberately

## Resolved Design Decisions

1. **Timeout budget**: Total wall-clock time for the entire quality doc generation must cap at **90 seconds**. This includes all parallel dimension agents + synthesizer. Given agents run in parallel, each dimension agent gets the full 90s budget minus synthesizer overhead (~15s), so effectively ~75s per dimension agent. If any agent exceeds the timeout, it fails (no fallback — see below).

2. **Domain discovery**: A lightweight domain discovery agent runs first (before dimension agents). It gets the tree diagram + language summary and produces a domain list with boundaries. This runs sequentially, but should be fast (~10-15s). Its output feeds into all dimension agents as shared context.

3. **Fallback granularity**: No fallback. If an agent fails, the entire quality assessment fails. This keeps the system honest — we'd rather surface a failure than silently degrade to deterministic scores the user didn't ask for. The orchestrator reports which agent(s) failed and why.

4. **Cost control**: Not a concern. We optimize for quality of assessment, not API call count.

## Implementation Phases

### Phase A: Deterministic foundations
- Build `quality_complexity_analyzer.rs` (nesting depth, branch count, function size)
- Add tree diagram generator (replace JSON tree with `ls -R`-style output)
- Build the file sampler: given a ranked file list + budget, pre-read files that fit in context
- Wire deterministic pre-computation step into the orchestrator

### Phase B: Domain discovery agent
- Build lightweight domain discovery agent prompt
- Wire into orchestrator as sequential Step 1
- Test against this repo + a few others to validate domain output format

### Phase C: Dimension agents (start with hybrids)
- `test_quality` (hybrid) — deterministic base score + agent spot-check of sampled test files
- `risk_exposure` (hybrid) — deterministic complexity ranking + agent review of top-risk files
- `agent_steering` (pure agent) — rubric is well-defined from research
- `test_coverage` (pure agent) — runs coverage tools natively
- Remaining dimensions (pure agent each)
- Each one: write prompt, test against this repo, compare to v1 scores

### Phase D: Synthesizer + end-to-end
- Build the synthesizer prompt
- Wire up full pipeline: pre-compute → domain discovery → parallel dimensions → synthesizer → grade doc
- Enforce 90s hard timeout at orchestrator level
- Fail-fast: any agent failure = entire assessment failure with clear error
- Update renderer to link to dimension reports

### Phase E: Cleanup
- Remove `quality_evidence_bundle.rs` and monolithic prompt builder
- Remove `truncate_bundle_for_agent()`
- Remove deterministic fallback logic (no longer needed — we fail instead)
